投資ユニバース分析プロダクト
==============

Design Doc（MVP v0.2）
--------------------

* * *

1. 目的とスコープ

----------

### 目的

* 日本株を対象に、複数ソース（JPX月次銘柄一覧＋MINKABU＋yfinance）からユニバースを構築し、  
  RS×出来高偏差を中心とした指標を算出して成果物（XLSX/CSV）を生成、Google Drive（Paid領域）へ格納する。

* PC常時稼働不要のため、**日次バッチはクラウド/仮想環境で実行**する。

### MVPでやること（追加反映）

* ユニバース作成（JPX月次銘柄一覧＋MINKABUスクレイピング＋yfinance）

* JPXに無いがMINKABUにある銘柄を**Pending**として取り込み（保留レーン）

* 指標算出

* 成果物生成（XLSX + 全マージCSV）

* Google Drive（Paid）格納

* 日次バッチのクラウド実行

### MVPでやらないこと

* 課金連動アクセス制御（Drive権限自動剥奪など）

* 日次通知

* Webダッシュボード

* 完全自動の課金PF更新（note自動更新等）

* * *

2. 全体アーキテクチャ（論理）

----------------

`[JPX 月次銘柄一覧] ─┐                    ├─> [銘柄マスター統合] ─> [Pending判定] [MINKABU スクレイプ] ┘  [Market Data (yfinance等)] ─> [前処理/正規化]                               ↓                         [Universe確定]                               ↓                        [Indicator算出]                               ↓                     [成果物生成 XLSX/CSV]                               ↓                 [Google Drive: /paid/YYYY-MM/]`

* * *

3. データソースと責務分担

--------------

### 3.1 JPX（月次銘柄一覧）

**役割：銘柄マスターの基準（ゴールド）**

* 上場銘柄集合の正統性担保

* 市場区分、銘柄コード、名称などの基礎属性

**運用**

* 月次で取得・更新（スナップショットとして保存）

* 日次バッチは「最新の月次スナップショット」を参照

* * *

### 3.2 MINKABUスクレイピング

**役割：JPXだけでは足りない補助・補完**

* JPX月次に反映される前後のタイムラグや、周辺メタ情報の補完に利用

* ただし「真の上場集合」はJPXを優先

**MVP要件：Pending銘柄**

* **MINKABUに存在するがJPX月次一覧に存在しない銘柄**を抽出し、`pending_listings`として保持する

* * *

### 3.3 yfinance（価格・出来高）

**役割：時系列（OHLCV等）取得**

* 修正後価格を前提（basisはメタで管理）

* 欠損や取得失敗があり得る前提で「再実行可能」な設計

* * *

4. 銘柄マスター統合とPending設計（追加要件）

---------------------------

### 4.1 マスターの優先順位

* **JPX月次**：正（canonical）

* **MINKABU**：補助（enrichment + gap detection）

### 4.2 Pendingの定義

* `MINKABUに存在` AND `JPX月次に存在しない`

### 4.3 Pendingの扱い（MVP方針）

* Pending銘柄は以下のどちらか（選択可能）で運用する  
  **A. MVPではユニバース算出から除外（推奨）**  
  **B. “Pending Universe”として別枠出力（監視用）**

理由：

* JPX基準に載っていない銘柄を通常ユニバースに混ぜると、分母の正統性が揺れる

* ただし見逃したくないので、監視レーンとして保持する価値は高い

### 4.4 Pendingの解消

* 月次JPX更新で該当銘柄が載ったら
  
  * pending → 正規listingへ昇格（履歴を保持）

* * *

5. ユニバース設計（MVP）

---------------

### 5.1 Universe分類

* **Core Universe**（通常）

* **IPO Universe**（新規上場期間）

* **Pending Universe（任意）**：監視専用（ユニバースに混ぜない）

### 5.2 IPO判定

* `listed_date`（公式が取れれば）

* 無ければ `first_trade_date`（推定）

* `age_days < IPO_THRESHOLD` → IPO Universe

※ 「120日前取得できない＝IPO」は採用しない（誤判定が多い）

### 5.3 Universe確定（T-1基準）

* 日次バッチ内で Universe Membership を確定し、日付付きで保存する

* 当日データに依存しない（欠損耐性）

* * *

6. 指標設計（MVP）

------------

### 6.1 RS

* RS_long（252営業日リターン順位/パーセンタイル）

* RS_short（63 or 126営業日、用途により）

* ΔRS（前日差）

※ IPO Universe：RSは原則未算出（代替指標は将来）

### 6.2 出来高偏差

* Core Universe：z-score（過去N日）

* IPO Universe：原則別ロジック（MVPでは未算出でも可）

-------------

### 7.1 XLSX（人間用）

* Sheet：Core / IPO /（任意でPending）/ 凡例

* 表示は上位N（例：20/50）＋全件はCSVで提供でも可

### 7.2 CSV（分析用・全マージ）

* 将来のBI/DB投入を前提に縦持ち

8. Google Drive格納設計（MVP）

------------------------

### 8.1 フォルダ分離（事故防止）

`/public/ /paid/   ├─ YYYY-MM/       ├─ latest.xlsx      ├─ latest.csv      ├─ (optional) run_manifest.json`

### 8.2 日次バッチの書き込み戦略（ロバスト）

* 生成物は一旦 `/paid/YYYY-MM/_staging/` に置く

* 完了後に `latest.*` を**原子的に差し替える**（中途半端なファイルを見せない）

### 8.3 欠損時

* `latest.*` を更新しない

* 前回の有効成果物が残る（仕様）

* * *

9. 実行環境（追加要件：ローカル非依存）

---------------------

### 9.1 要件

* PCの連続稼働不要

* 定時起動不要（クラウドスケジューラで実行）

* 再実行・ログ追跡が可能

### 9.2 実装候補（MVP推奨順）

**A. GitHub Actions（最有力）**

* cron実行

* secrets管理（Drive API鍵など）

* ログ閲覧が容易

* コスト低

* 失敗通知も最小工数で可能

**B. GCP Cloud Run + Cloud Scheduler**

* さらに堅牢

* 将来拡張しやすい

* 初期設定はやや増える

**C. AWS（Lambda/ECS + EventBridge）**

* 同上。運用色が強い。

MVPでは **Aが最短**。

### 9.3 運用上の隘路（クラウド実行）

* スクレイピングは
  
  * 失敗/ブロック/HTML変更の確率がある  
    → リトライ・フェイルセーフ必須

* Secretsの漏洩防止（Drive鍵、APIキー等）

* 実行時間上限（Actionsのタイムアウト）  
  → 初回バックフィルは分割運用が前提

* * *

10. ロバストネス要件（構造＋運用）

-------------------

### 10.1 構造的工夫

* Universe Membership を日付付き確定保存（分母固定）

* Pendingレーン導入（正統性の揺れを隔離）

* Driveは staging→latest の二段階コミット

* 欠損日は前回成果物が残る仕様（信用毀損を防ぐ）

### 10.2 運用上の隘路と対策

| リスク            | 影響      | 対策                               |
| -------------- | ------- | -------------------------------- |
| MINKABU HTML変更 | スクレイプ失敗 | 「失敗してもJPX基準で動く」/ Pending更新のみ失敗許容 |
| yfinance欠損     | 指標欠損    | 欠損銘柄は当日除外・バックフィル待ち               |
| 初回データ量が重い      | タイムアウト  | 初回は“候補群のみ”/ バックフィルを分割            |
| Drive更新途中で中断   | 中途半端露出  | staging→latest のみ公開              |
| JPX月次の更新遅れ     | 銘柄漏れ    | Pendingで吸収、翌月昇格                  |

12. 仕様のまとめ（MVPの思想）

------------------

* **正統性**：JPX月次を基準にする

* **見逃し防止**：MINKABUでPendingを拾うが、通常分母に混ぜない

* **継続性**：クラウド実行＋欠損許容＋原子更新で信用を守る

* **将来拡張**：成果物はXLSX/CSVで固定し、PF変更に耐える
